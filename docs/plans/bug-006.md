## Approach
Both tools take an optional FastMCP `Context` (`ctx: Context | None = None`, which FastMCP injects
and keeps out of the input schema) and hand it to `run_screenshot_sync`. A small `ProgressReporter` in `app/mcp/progress.py` reports `done/total` after each row through a new `on_step`
callback on `LocalizationScreenshotService.apply_sync`, and a background heartbeat re-sends the last
state every `PROGRESS_HEARTBEAT_SECONDS` while a row is slow. A second apply on the same
(app, target version) is refused while the first runs. Rejected: reporting from inside
`apply_sync_step` per upload — it would put MCP plumbing into the service layer, and one report
per row plus the heartbeat already stays under the 300 s limit.

## Sequence
1. Red tests for progress per row (both tools), the heartbeat, the no-context no-op and the lock.
2. `on_step` on `apply_sync` (service stays MCP-agnostic).
3. `SyncProgress` + wiring in `run_screenshot_sync` and both tools.
4. Per-page apply guard.

## Files
| File | Change |
|------|--------|
| backend/app/mcp/progress.py | New: `SyncProgress` reporter with heartbeat |
| backend/app/services/asc/screenshots.py | `apply_sync(..., on_step=None)` |
| backend/app/mcp/tools/screenshots.py | `ctx` on `screenshots_sync`, progress + guard in `run_screenshot_sync` |
| backend/app/mcp/tools/cpp.py | `ctx` on `cpp_screenshots_sync` |
| backend/tests/test_mcp_screenshots.py | Regression tests |

## Tests first
- `screenshots_sync` apply with a recording context reports `(k, 3)` for k = 1..3 (one per row). Fails: nothing is reported.
- `cpp_screenshots_sync` apply, same. Fails: nothing is reported.
- A row slower than the heartbeat interval produces heartbeat reports during it. Fails: nothing is reported.
- A dry run and a call without a context report nothing and still return the plan.
- `ctx` is not in either tool's input schema.
- A second apply on the same page while one runs is a `ToolError`; the guard is released afterwards, also after a failure.

## Risks
- The client disconnects and `send_progress_notification` raises mid-apply → a half-replaced set.
  The reporter logs and swallows send failures; progress is advisory.
- The guard is in-process only; a multi-worker deployment would need a DB or Redis lock. The
  backend runs one worker.

## Deviations
- The reporter is `ProgressReporter` (generic, not sync-specific), not `SyncProgress`.
- The guard keys the ASC version id alone, not (app, version): two local app rows for one ASC app must share it.
- Review: the guard is held from the plan on, not only around `apply_sync`, because a plan read while another apply writes is stale.
- Review: the cancel path is tested; the heartbeat is reaped with `gather` so a cancel of the tool call propagates.
