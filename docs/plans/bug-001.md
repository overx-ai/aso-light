# Plan: bug-001 — Reviews module cross-app IDOR

## Approach

ASC scopes `/v1/customerReviews/*` and `/v1/customerReviewResponses/*` to the whole Apple
team, not per app. `list_reviews` is app-scoped (`GET /v1/apps/{asc_app_id}/customerReviews`);
every other entry point (`get_review`, `draft`, `translate`, `create_response`,
`update_response`, `delete_response`) takes a bare `review_id`/`response_id` with no proof it
belongs to the caller's verified app. The live-ASC-verification alternative (re-querying Apple
for the review's parent app, the same technique `ASCPricingService` uses for subscription
children) is not available here — Apple exposes no reverse "which app owns this review" lookup.

**Table design.** Two small mapping tables, modeled directly on the existing
`ReviewThemeCache` pattern (`app/models/review_theme.py`) — this codebase already uses a DB
table as "cache what an external API told us" state for reviews, not a filesystem cache
(that's reserved for the large price-point dataset):

- `review_app_map(review_id STR PK, app_id INT FK->apps.id ON DELETE CASCADE, updated_at)`
- `review_response_map(response_id STR PK, review_id STR indexed, updated_at)`

`review_id` is the primary key of the first table (Apple review ids are globally unique across
the team) — a plain unique-indexed int `id` PK would add nothing. `response_id` is likewise the
PK of the second table. `review_response_map.review_id` is a plain indexed string, NOT a hard FK
into `review_app_map` — it is populated at the same moments as `review_app_map` but the two
writes are not required to be transactionally coupled beyond "same session", and decoupling
avoids a FK-constraint failure if population order ever changes.

**Population strategy.** `list_reviews` always requests `include=response`, so a single page
already carries both review ids and (for reviews with a developer response) the response's id
via `relationships.response.data.id`. A new module, `app/services/reviews/ownership.py`,
provides `record_review_app_mappings(session, app_id, items_raw)` — bulk-fetches any existing
rows for the ids in the page (one SELECT, mirroring `app.services.reviews.themes
.upsert_classifications`'s "bulk fetch, no dialect-specific ON CONFLICT" pattern for SQLite/
Postgres portability) and upserts both tables in one pass. This is called from `list_reviews`
(REST + MCP) and, defensively, from `get_review`/`draft`/`translate` (their `svc.get_review`
call returns the same JSON:API shape for a single review, wrapped in a list) so the map stays
fresh even between `list_reviews` calls. `create_response` additionally records its own
`response_id -> review_id` pair immediately after ASC returns the newly created response's id
(list_reviews would not otherwise learn about it until the next page fetch).

**Fail-closed rule.** `assert_review_belongs_to_app(session, review_id, app_id)` 404s
(`ChildResourceNotFoundError`, mirroring the existing exception `ASCPricingService` raises for
the identical "child not proven to belong to parent" shape) unless `review_id` has a row in
`review_app_map` whose `app_id` matches. A review never observed by `list_reviews` for ANY app
is indistinguishable from a foreign one and 404s identically — no leniency, no distinguishing
"never seen" from "belongs to someone else" (that distinction itself would leak existence).
`assert_response_belongs_to_app(session, response_id, app_id, review_id=...)` resolves
`response_id -> review_id` first (also 404 if unseen), then — when a path `review_id` is
supplied (REST only; MCP's `update_response`/`delete_response` never took one) — asserts it
matches the resolved review_id, then delegates to `assert_review_belongs_to_app`.

**Where the assert runs.** Before building an `ASCClient` for the app, not after — a 404 from
our own DB map shouldn't pay for a credential decrypt + client construction it doesn't need.

## Sequence

1. Write failing reproduction tests (`tests/test_review_app_map.py`) — two apps, list under app
   A only, then hit all 6 entry points (REST + MCP) with app B's ids while authorized for app A.
   Confirm they fail against current `main`-equivalent code (no map, no assert).
2. Add `ReviewAppMap` / `ReviewResponseMap` models + Alembic migration.
3. Add `app/services/reviews/ownership.py` (record + assert helpers).
4. Wire into `app/api/v1/reviews.py` (REST) and `app/mcp/tools/reviews.py` (MCP): population in
   `list_reviews`/`get_review`/`draft`/`translate`/`create_response`; assertion in all 6 write/
   read entry points named in the bug.
5. Add positive regression test: same-app access continues to work unchanged.
6. Run full `test_reviews.py` + new tests + full suite.
7. Fill in the bug doc's `## Fix` / `## Regression test` sections, commit.

## Tests first

`tests/test_review_app_map.py`, following the seeding pattern in `tests/test_asa_joins.py` /
`tests/test_subscription_swap_fixes.py` (real SQLite via `async_session_factory`, two
`User`/`ASCCredential`/`App` triples under, per the bug's repro, *different* credentials — the
IDOR is about cross-tenant/cross-app leakage regardless of whether the underlying Apple team is
shared; using two separate ASO-Light users is the stricter, more realistic condition and
subsumes the "same Apple team, different ASO-Light app" case from the bug's repro paragraph):

- `list_reviews` called for app A only, populating the map for app A's reviews/response.
- For each of `get_review`, `draft_review_reply`, `translate_review`, `create_reply`
  (`create_response`), `update_reply`, `delete_reply` — REST route function called directly
  (this repo has no `TestClient` convention; see `test_reviews.py`'s module docstring) and the
  MCP tool function called directly — assert a 404 (REST, via `HTTPException`) / `ToolError`
  (MCP) when passed app B's `review_id`/`response_id` while authorized for app A.
- Positive case: the same 6 entry points succeed against app A's own ids after `list_reviews`
  has populated the map for app A.
- Full existing `tests/test_reviews.py` suite must stay green (it exercises the same functions).

## Risks

- **Select-then-insert race under concurrency.** Two concurrent `list_reviews` calls that both
  observe a not-yet-mapped `review_id` could both attempt an INSERT, and the loser hits a
  primary-key `IntegrityError` instead of an upsert. This is the same tradeoff
  `app.services.reviews.themes.upsert_classifications` already accepts in this codebase (no
  dialect-specific `ON CONFLICT`, for SQLite/Postgres portability) — not a new risk class, but
  worth flagging: worst case is a transient 500 on one of the two racing requests, not an
  incorrect authorization decision. A retry succeeds.
- **Pre-fix / never-listed reviews 404 by design.** A review that predates this fix, or that a
  caller reaches via `get_review`/`draft`/`translate`/MCP without ever calling `list_reviews`
  first, is unmapped and 404s even for its rightful owner. This is the documented, intended
  fail-closed behavior (bug doc: "this only bites deliberate ID-guessing or genuinely stale/
  foreign IDs") — flagging it here so it's a known tradeoff, not a surprise.

## Deviations

- **MCP `update_response`/`delete_response` did not gain a `review_id` parameter.** The bug doc's
  "stop discarding the route's `review_id`; actually use it" instruction describes the REST route,
  which already had (and discarded) a `review_id` path param. MCP's `reviews_update_response` /
  `reviews_delete_response` never took one — adding one would change the public tool signature for
  no security benefit, since the same protection (resolve `response_id -> review_id -> app_id`,
  404 on mismatch) is achieved without it. `assert_response_belongs_to_app` accepts `review_id` as
  an optional keyword specifically so REST can pass it (cross-checking the path param against the
  resolved value) while MCP omits it (nothing to cross-check against). Both call sites still run
  the identical core assertion.
- **Two independent tenants in the repro, not "same Apple team, two ASO-Light apps."** The bug's
  repro paragraph describes one Apple team shared by two apps under possibly-different or the
  same ASO-Light user. The test seeds two fully independent users/credentials/apps instead — the
  stricter condition (cross-tenant, not just cross-app) that subsumes the milder one, and matches
  how `tests/test_asa_joins.py` / `tests/test_subscription_swap_fixes.py` already seed IDOR
  fixtures in this repo.
- **`ChildResourceNotFoundError` reused, not a new exception type.** The plan considered a
  reviews-specific exception but the existing type's semantics ("child id not proven to belong to
  its verified parent" -> 404 REST / ToolError MCP) are identical; only its docstring needed
  broadening. Keeps `app/services/asc/errors.py` as the single source of "this shape of IDOR
  guard" across pricing and reviews.
- No deviation on the table design, population strategy, or fail-closed rule as planned.
